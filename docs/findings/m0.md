| | |
|---|---|
| Date | 2026-11-12 (review fixes applied the same day) |

M0 rendered 14 fixtures in Chromium and as UI Toolkit twins in Unity, and compared boxes, text lines, colours and
pixels. This document turns the measurements into rules, lowerings, text styles, thresholds and the verifier setup
that M1 builds on. Every number below comes from the runs in "Reproduction"; outputs are git-ignored under
`spike/out/`. Measured results and values derived from them are kept apart; derived ones are labelled.

## 1. Decisions at a glance

| Risk | Decision |
|---|---|
| R1 layout | Flexbox parity holds within 0.5 px for fixed, grow/shrink/basis, %, min/max, absolute and wrap layouts. Two layout differences become lint errors: U-CSS-018 (baseline alignment) and U-CSS-019 (automatic minimum size). Radii are resolved to px at export, with U-CSS-020 for elliptical radii; U-CSS-021 rejects dashed/dotted borders and U-CSS-022 gradient stops closer than the 64-step ramp |
| R2 line height | Font sizes are multiples of 4 px (Unity rounds font sizes to whole device pixels, O-13); CSS `line-height` = fontSize × 2478/2048 rounded to 1/64 px (Chromium LayoutUnit), so Chromium's line pitch equals UI Toolkit's unrounded pitch. | R3 bold | Only weights with a real face. Kit sync is the primary check; lint U-FONT-001 is the backstop for the reference locale's font; W-FONT-001 stays a warning for other locales |
| R4 font twin | `FontAsset.CreateFontAsset(Font, 72, 7, SDFAA, atlas, atlas, Dynamic, multiAtlas: true)` with the TMP asset's settings; weight table filled through the live `fontWeightTable` array; face metrics equal TMP's |

## 3. R1 layout: rules and lowerings

Matches without any rule: fixed sizes, margins, `justify-content`, `align-items` (except baseline), `align-self:
stretch` (f01: 0 px); `flex-grow`, `flex-shrink`, `flex-basis` (f02: ≤ 0.5 px from whole-pixel snapping); `%` sizes in
auto-sized parents (f03: 0 px); explicit `min-width`, `min-height`, `max-width` under shrink (f04: 0 px);
absolute children with insets, `%` insets and left+right stretch, and an absolute child without insets, which UI
Toolkit also puts at the CSS static position (f05: 0 px); `flex-wrap` with margins and `align-content: flex-start`
(f06: 0 px); per-side border widths and colours, uniform and per-corner radii, `border-radius: 50%` on a square,
rounded `overflow: hidden` clipping (f14); solid and alpha colours, `opacity` (f10).

Not measured in M0, although spec §5.3 allows them: `rotate`/`scale`/`translate`/`transform-origin`, `aspect-ratio`,
`text-shadow`, `letter-spacing`, `word-spacing`, `white-space` beyond explicit line breaks, `text-overflow`,
transitions (O-15).

The fixtures mirrored UI Toolkit's initial values in their HTML base rules (column flex, `position: relative`,
`flex-shrink: 1`, `box-sizing: border-box`, `align-content: flex-start` on wrapping rows). Where CSS and USS initial
values differ, designs that rely on the CSS initial value were not measured; the compiler must write such values
explicitly or lint must reject them (open item O-6).

New lint rules (numbering continues the existing U-CSS-001..017; the full rule list with fixes is published in
`design-kit/RULES.md` with the kit in M1, and spec §5.3–5.5 summarise it) and lowerings:

| Id | Severity | Fails when | Fix hint | Evidence |
|---|---|---|---|---|
| U-CSS-018 | error | `align-items` or `align-self` is `baseline`, `first baseline` or `last baseline` | Use `flex-start`, `center` or `flex-end`; to line up two text styles, give the smaller one a top margin equal to the difference of their baselines | USS rejects the value (importer: `Expected (flex-start \| flex-end \| center \| stretch \| auto) but found 'baseline'`); f09-bl-a lands 11 px lower |
| U-CSS-019 | error | A flex item's box changes when its `min-width` / `min-height: auto` is replaced by `0` (the design relies on CSS's automatic minimum size). Lint re-lays out the page once with `min-*: 0` on every flex item whose value is `auto` and compares boxes | Give the item an explicit `min-width` (row) or `min-height` (column) in px, or `flex-shrink: 0`, or make the container large enough. UI Toolkit treats `auto` as 0 and breaks long words instead | f04-auto-text: Chromium keeps the unbreakable word at 396.06 px; UI Toolkit shrinks it to 266 px and wraps it into 2 lines; its sibling moves 130.06 px |
| U-CSS-020 | error | A corner's horizontal and vertical radii differ after resolution (CSS `/` syntax, or a `%` radius on a non-square box) | Use one px radius per corner; for a pill use half the height | USS radii are circular per corner; only `50%` on a square box was measured |

## 4. R2 line height and text styles

**Current rule (after the O-13 gate).** The gate below failed: the Unity capture showed that Unity 6000.3 rounds font
sizes to whole device pixels. A style declared as 16.515625 px renders at 17 px at scale 1, 12 px at scale 0.75 and
8 px at scale 0.5 (evidence: Unity capture of the style at the three viewport scales). Fractional kit font sizes cannot
be reproduced, so the kit now uses:

- font sizes that are multiples of 4 px, from {12, 16, 20, 24, 28, 32, 40, 48, 56, 64}: `size × 0.75` and `size × 0.5`
  are then whole device pixels at 2560×1440, 1920×1080 and 1280×720;
- CSS `line-height = fontSize × (ascent + descent) / unitsPerEm` of the reference font, rounded to the nearest 1/64 px
  (Chromium's LayoutUnit), so Chromium's line pitch equals UI Toolkit's unrounded pitch `P`. For Inter (hhea ascender
  1984, descender 494, 2048 units per em) the ratio is 2478/2048 = 1.2099609375.

Heights then differ only by Unity's ceil (< 1 px) and baselines by < 0.5 px, with no line-count limit, because the
per-line pitch is equal (exact for sizes 16, 32, 48, 64, whose product is a multiple of 1/64; otherwise within 1/128 px
per line from the rounding). Chromium serialises computed lengths to 6 significant digits (`19.3594px` for 19.359375);
lint U-CSS-016 matches numerically with a tolerance, which covers it.

### Superseded: fractional size table (kept as history)

The text below, including the table, describes the earlier ruling (fractional font sizes just below multiples-of-4
line heights, gated by O-13). It is superseded by the rule above and no longer matches `text-styles.json`.

Measured rules (f07, f09, f13):

- UI Toolkit text element height = `ceil(n × pitch)`, with `P = fontSize × faceInfo.lineHeight / faceInfo.pointSize`
  (Inter: 87.1171875 / 72 = 2478/2048 = 1.2099609375 × fontSize; equal to `ascentLine − descentLine`, no line gap).
  The rule reproduces every measured height (12–48 px, 1–3 lines). USS has no line-height, so CSS `line-height` is
  ignored.
- **The two text generators differ in pitch.** Standard: pitch = `P` unrounded (caret line heights 16.9395 /
  21.7793 / 24.1992 / 29.0391 / 48.3984 at 14/18/20/24/40 px). Advanced: pitch = `P` floored to 1/64 px (16.9375 /
  21.765625 / 24.1875 / 29.03125 / 48.390625). Element heights and first-line baselines were equal for the measured
  1–3 lines; long texts differ, so the line limits below are given per generator.
- Baseline = line top + ascent, unrounded, in both generators.
- Chromium with `line-height: normal`: line box `round(ascent) + round(descent)`, so single lines at 18/20/24 px are
  1 px shorter than in UI Toolkit (21/24/29 vs 22/25/30) and 16 px text with 2–3 lines is 1 px taller (40/60 vs
  39/59). Stacked labels accumulate it (f09 +3 px after three rows).
- Chromium with a fixed integer `line-height: L`: element height `n × L` exactly (f07: 20/40/60, 24/48/72, 28/56/84,
  40/80/120); baseline = `round(ascent) + floor((L − round(ascent) − round(descent)) / 2)` (f07: 15, 18, 21, 31).

**Decision.** A kit text style sets CSS `line-height: L`, where L is a multiple of 4 px, and `font-size: f`, where f is
the largest multiple of 1/64 px with `L − P ≥ 0.001 px`. Then `ceil(P) = L`: one line is exactly L tall in both
engines, the baseline differs by at most 0.43 px, and the drift per line, `L − P`, is 0.0015–0.02 px (standard) or at
most 0.031 px (advanced, pitch floored to 1/64).

- *Why just below and not `P = L`:* for Inter `P = f × 2478/2048`, so `P = L` needs `f = L × 1024/1239`, which has no
  finite decimal or binary form. CSS text, float32 and the USS file all store a rounded value. Rounded up, `P > L` and
  UI Toolkit's ceil makes every text element 1 px taller; no ceil tolerance smaller than the smallest measured
  fraction (0.039, at 24 px) is known.
- *Why 1/64:* exact in float32, in Chromium's LayoutUnit and in 26.6 fixed point, and at most 6 decimals; the advanced
  generator already works at 1/64, so the size is not quantised again.
- *Why the 0.001 margin:* it absorbs float error even if UI Toolkit's ceil has no tolerance. It only changes `body`
  (23.140625, margin 0.00075, becomes 23.125).
- *Why multiples of 4:* `L × scale` is then a whole device pixel at the M1 viewport scales 0.75 (1920×1080) and 0.5
  (1280×720), where UI Toolkit is expected to round text height up to the device-pixel grid. **Derived** from the
  measured whole-pixel rounding at scale 1; confirmed in O-2.

**Kit sync and tooling.**

- Kit sync derives each style's `fontSize` from its `lineHeight` and weight and the reference locale's font twin
  (`faceInfo.lineHeight / faceInfo.pointSize`) with the rule above. The committed `text-styles.json` is the Inter
  instance; another project's kit gets its own sizes. Sync fails when a line height is not a multiple of 4 or a
  weight has no real face (R3).
- Chromium serialises computed lengths to 6 significant digits (`16.5156px` for 16.515625). Lint U-CSS-016 therefore
  matches `font-size` and `line-height` numerically with a tolerance (0.001 px is ample), not by string.
- The IR records the matched style name, so the compiler writes the kit's exact value, not the serialised one.
- The USS writer formats numbers with `CultureInfo.InvariantCulture` at round-trip precision; a Turkish culture
  would otherwise write `16,515625`.

## 5. R3 bold policy

f08 advance widths (caret route):

| Text | Chromium | UITK standard | UITK advanced |
|---|---|---|---|
| Regular 32 px | 381.00 | 381.03 | 381.00 |
| Real bold 32 px (weight table) | 392.08 | 392.11 | 392.08 |
| Synthetic bold 32 px | 381.00 | **434.79** | 381.00 |
| Real bold 16 px | 196.05 | 196.05 | 196.14 |
| Synthetic bold 16 px | 190.50 | **217.39** | 190.58 |

The standard generator widens every advance by 14.1 % when it synthesizes bold; Chromium keeps the advances. With
the real face in the weight table both engines agree within 0.03 px. Decision: the kit allows 400 and 700 only, both
real faces. The primary check is kit sync, which fails a text style whose weight has no real face in the reference

coincides with U-CSS-016 while the kit's styles are 400/700. W-FONT-001 stays a warning for the other active locales,
which are checked structurally. The advanced generator keeps advances for synthetic bold; using it for such locales
is open item O-8.

## 6. R4 font twin

- TextCore `FontAsset.CreateFontAsset(Font font, int samplingPointSize, int atlasPadding, GlyphRenderMode
  renderMode, int atlasWidth, int atlasHeight, AtlasPopulationMode atlasPopulationMode, bool
  enableMultiAtlasSupport)` (public). The twin copies sampling point size, padding, render mode and atlas size from the
  TMP asset (measured with the first consumer project's reference settings: 72, 7, `SDFAA` (4165), 2048×2048 regular,
  1024×1024 bold), always `AtlasPopulationMode.Dynamic`, multi-atlas on.
- Face metrics come from the TTF and equal the TMP asset's: pointSize 72, lineHeight 87.11719, ascentLine 69.75,
  descentLine −17.36719, for both Regular and Bold.
- Weight table: `fontWeightTable` has an internal setter but its public getter returns the live array;
  `twin.fontWeightTable[7].regularTypeface = boldTwin` sticks, and `-unity-font-style: bold` then renders the real
  Bold face (392.11 vs Chromium 392.08). The generator saves the twin after the assignment.
- `TMP_FontAsset` cannot be used by UI Toolkit: it derives from `TMP_Asset`, not TextCore `FontAsset`; a cast throws
  `InvalidCastException`; USS `-unity-font-definition: url(<TMP asset>)` imports with "Unsupported type TMP_FontAsset"
  and resolves to no font. Twins are required.
- The dynamic twin works with `-unity-text-generator: advanced` (pitch floored to 1/64, see R2).
- Advances vs Chromium: |Δ| ≤ 0.03 px (standard), ≤ 0.09 px (advanced). Fallback-table mirroring was not measured
  (O-7).

## 7. R5 capture route

All three routes rendered pixel-identical images in batchmode on Metal: editor update ticks in an EditMode test
(public API only), internal `UIElementsRuntimeUtility.RepaintPanel`/`RenderPanel`, and Play mode entered from the
EditMode test (39 of 39 PNGs identical between the Play and EditMode runs). Play mode reloads the domain in the
fixture project and re-runs `OneTimeSetUp`, so it only adds risk.

Decision for the verifier:

- **Route:** an EditMode `UnityTest` that drives the capture with `yield return null` (editor updates), public API
  only. No Play mode, no windowed clone. The clone tool runs EditMode tests only; that is sufficient.
- **Entry:** `scripts/unity-check.sh --warm --editmode "<capture test name>" --wait` (a warm, reused batch clone of the
  project), with the request passed in environment variables, which reach the test process (the spike used
  `SPIKE_OUT`, `SPIKE_TARGET`, `SPIKE_ROUTE`, `SPIKE_ONLY`). Without the clone tool the same test runs with Unity
  `-batchmode -runTests -testPlatform EditMode -testFilter <name>` on a copy of the project. The capture is therefore
  an EditMode test, not a PlayMode test and not an `-executeMethod` entry (such an entry would have to keep the
  editor ticking until the panel has rendered; that route was not measured).
- **Panel:** `UIDocument` on an inactive host (activated after `panelSettings` and `visualTreeAsset` are set);
  `PanelSettings` with `themeStyleSheet = null`, `scaleMode = ScaleWithScreenSize`, `referenceResolution` 2560×1440,
  `screenMatchMode = MatchWidthOrHeight`, `match` from the profile, `clearColor = true` with a sentinel colour
  (magenta) whose remaining pixels mean "not covered", `forceGammaRendering = true`, `targetTexture` = a RenderTexture
  of the viewport size, `R8G8B8A8_UNorm`, depth-stencil `D24_UNorm_S8_UInt` (rounded clipping uses the stencil).
- **Scale formula:** `PanelSettings.ResolveScale` (decompiled, 6000.3.6f1) blends the width and height ratios
  linearly: `scale = lerp(W/refW, H/refH, match)`. This equals the UGUI CanvasScaler log formula
  `2^lerp(log2(W/refW), log2(H/refH), match)` only at the reference aspect; the M0 viewports were all 16:9, so the
  difference was not visible here. The exporter (`logicalViewport`) uses the linear formula.
- **Document root:** without a theme the `UIDocument` root is not stretched (f01: `0,0,2560,960`, 1,228,800 magenta
  pixels); the capture sets it to `position: absolute; left/top/right/bottom: 0` (magenta 0). Because the capture
  is theme-less, the compiled USS must reset the control styles a runtime theme adds (margins, padding, borders and
  backgrounds of `Label`, `Button`, …), so the screen looks the same in game under the project's theme (O-3).
- **Timing:** 10 editor updates after mount, the stretch, 10 more; 5 after each state change or pointer event.
  A capture (mount, frames, readback, PNG, boxes) took 65–183 ms; a 14-fixture run took 16 s of Unity time on the warm
  clone.
- **Readback:** `ReadPixels` into `Texture2D(RGBA32, mipChain: false, linear: true)` or `AsyncGPUReadback.Request(rt,
  0)`; both gave identical bytes (0 of 3,686,400 pixels differ), upright. The bytes are written to the PNG unchanged.

## 8. R6 pseudo-states

Working sequence (identical in Play and EditMode):

```csharp
var e = new Event { type = EventType.MouseMove, mousePosition = el.worldBound.center, button = 0 }; // panel coordinates
using (var evt = PointerMoveEvent.GetPooled(e)) panel.visualTree.SendEvent(evt);   // :hover now, styles next update
e.type = EventType.MouseDown; e.clickCount = 1;
using (var evt = PointerDownEvent.GetPooled(e)) panel.visualTree.SendEvent(evt);   // :active, only with a Clickable
e.type = EventType.MouseUp; e.clickCount = 0;
using (var evt = PointerUpEvent.GetPooled(e)) panel.visualTree.SendEvent(evt);     // back to :hover
// reset: PointerMoveEvent outside every element (e.g. 2500,1400) -> no pseudo-state
```

- Hover styles resolve one update after the event; active styles within 3. `:hover` works on any element.
- **`:active` only applies to elements with a `Clickable` manipulator** (`Button` has one). A plain `VisualElement`
  stays `Hover` after `PointerDownEvent`; Chromium applies `:active` to any element. Hence the compiler lowering in §3.
- UI Toolkit hovers one element at a time, so the capture matrix has one job per element and pseudo-state.
- **Unmeasured, ancestors:** CDP `CSS.forcePseudoState` forces only the target node, while a real pointer in UI
  Toolkit, as in Chromium, also hovers the target's ancestors. A design with a `:hover` rule on a parent of the
  target would differ between golden and capture; the exporter may have to force hover on the ancestors too (O-5).
- Not measured: `:focus`, `:disabled`, `:checked`, transitions on pseudo-state rules, and other viewport scales
  (O-5).

## 9. R7 text lines

- Route: for `i = 0..text.Length`, `TextElement.selection.GetCursorPositionFromStringIndex(i)` (public in 6000.3,
  both generators). `x` is the caret position, `y` the bottom of the caret's line. Indices with the same `y` (±0.5)
  form a line; a line's width is its largest `x`, its top the previous line's bottom; baseline = line top +
  `faceInfo.ascentLine × fontSize / faceInfo.pointSize` of `resolvedStyle.unityFontDefinition.fontAsset`. Convert with
  `LocalToWorld`, then to device pixels.
- Agreement: line counts equal in every text element of f07, f08, f09 and f13 (the only mismatch is the U-CSS-019
  case); widths |Δ| ≤ 0.03 px (standard), ≤ 0.09 px (advanced); first-line baselines |Δ| ≤ 0.5 px (Chromium rounds
  the ascent, UI Toolkit does not). The internal `textInfo` route gives the same numbers on the standard generator
  only and is not used.
- Fallback when `selection` is unavailable: line count = `round(contentHeight / P)`; break positions are then
  reported as "not compared". Not needed in 6000.3. Rich-text strings (tags change the string indices) were not
  measured (O-9).

## 10. R8 colour and SVG

| RenderTexture setup | f10 mean / max ΔE2000 (327 samples) | f11 mean / max ΔE2000 (151 samples) |
|---|---|---|
| `R8G8B8A8_SRGB`, forceGammaRendering off (Unity default in a Linear project) | 7.29 / 22.32 | 2.90 / 22.28 |
| `R8G8B8A8_UNorm`, off | 8.61 / 26.23 | 18.62 / 27.48 |
| **`R8G8B8A8_UNorm`, on** | **0.15 / 0.72** | **0.35 / 9.56** (hard stop; 0.89 without it) |
| `R8G8B8A8_SRGB`, on | 16.09 / 28.33 | 20.16 / 28.77 |

- Opaque colours match in the default setup too; alpha blending does not: in a Linear project UI Toolkit blends in
  linear space, Chromium in sRGB space (25 % white over `#0b1f26`: Chromium `#48575c`, default `#8a8b8d` ΔE 22.32,
  UNorm + forceGamma `#48575c` ΔE 0).
- **Verifier decision:** `R8G8B8A8_UNorm` target with `forceGammaRendering = true`; readback bytes are written
  unchanged (no gamma conversion anywhere). This setup also makes f01–f06 pixel-exact (0.00 % of pixels off by more
  than 3).
- **In game:** `forceGammaRendering` stays **off** for panels without a UNorm `targetTexture`, which includes every
  ordinary on-screen panel. The Unity 6000.3 Scripting Reference for
  [`PanelSettings.forceGammaRendering`](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/uielements/panelsettings/forcegammarendering)
  states the flag applies only in a linear project "when the panel is being rendered into a Render Texture with a
  compatible format (e.g. R8G8B8A8_UNORM)". M0's only other data point agrees: on an sRGB target the flag
  double-encodes (ΔE 28.33).
- **Consequence in game:** on-screen panels blend in linear space, so alpha-blended colours drift from the design. The
  closest measured analogue is the sRGB RenderTexture, with up to ΔE 22.32.
- **Pilot candidate (O-1, spec R9):** the documented route. Render the UI into a UNorm RenderTexture with the flag on,
  then composite it over the camera's sRGB output with a custom shader. The same page describes an `ImmediateModeElement`
  drawing a full-screen quad that blends both. Its documented costs are extra RenderTexture bandwidth and a
  linear-to-gamma conversion per texture sample.
- **SVG:** the core importer `Unity.VectorGraphics.Editor.SVGImporter`, `svgType = SVGType.VectorImage` (enum
  value 3), defaults `gradientResolution = 64`, `tessellation = AntialiasedArcEncodings`, `preserveViewport = false`;
  applied with `style.backgroundImage = new StyleBackground(vectorImage)`. Opaque linear, 3-stop, angled and radial
  gradients match Chromium's sRGB interpolation within ΔE 0.83; `stop-opacity` and `gradientTransform` (CSS ellipse)
  import correctly. The 64-step ramp bands (88 distinct colours over 400 px vs Chromium's 194; ΔE ≤ 0.83) and smears
  hard stops (U-CSS-022).

## 11. Thresholds

`tools/design-export/fidelity-thresholds.json`: `{"boxPx":1,"baselinePx":1,"deltaE2000":1,"ssimNonText":0.99,"ssimElement":0.99}`.

| Key | Value | Evidence |
|---|---|---|
| `boxPx` | 1 (kept) | Layout boxes ≤ 0.5 px (whole-pixel snapping); text boxes 0 px with kit styles. Every miss above 1 px has a rule or a style decision |
| `baselinePx` | 1 (kept) | First-line baselines ≤ 0.5 px at all sizes; later lines stay within 1 px for the line counts in §4 |
| `deltaE2000` | 1 (kept) | Verifier setup: f10 ≤ 0.72, f13 ≤ 0.71, f12 ≤ 0.29, opaque and alpha gradients ≤ 0.89 |
| `ssimNonText` | 0.99 (kept) | Clean fixtures ≥ 0.99998. Gradient banding lowers it (f11's 22 % of gradient area: 0.99958, so a full-screen gradient is about 0.998). It cannot detect element-sized defects: f14 (pill + dashed) 0.9974 and f12 (four missing shadows) 0.9953 both pass. A coarse whole-capture gate only |
| `ssimElement` | 0.99 (new) | The same SSIM over each visible non-text element (≥ 16×16 px), over the element box joined with its baked-shadow rect. Of 137 elements measured, every one without a known defect is ≥ 0.9956 (lowest: a rounded clip edge). Defects: pill as ellipse 0.721, missing glow 0.873, missing hard shadow 0.955, missing large soft shadow (40 px blur, 8 px spread) 0.985, dashed as solid 0.969 |

**Shadow rect.** The region of an element with a baked shadow is the bounding box of its golden box and the shadow
rect from the IR's `shadow` field. `offset.x/y` is the shadow image's top-left relative to the element's border box,
and `offset.w/h` is the image size minus the element size. So the rect is (x + offset.x, y + offset.y, w + offset.w,
h + offset.h). Measured on the unbaked f12 shadows (rects from the CSS, grown by blur + spread):

| Element | Box only | Box + shadow |
|---|---|---|
| hard shadow `10px 10px 0` | 0.998 | 0.955 |
| large soft shadow `0 12px 40px 8px` | 0.997 | 0.985 |
| small soft shadow `0 8px 24px` | 0.999 | 0.994 |

The shadow rect turns the hard and the large soft shadow into failures.

**Limitation (dilution).** SSIM is averaged over the whole region, so a defect covering a small part of it is diluted:

- The missing small soft shadow (50 % black over a dark background) still passes at 0.9939. Faint shadows need the
  colour or pixel checks of O-12.
- A parent region dilutes further: one missing soft shadow inside a 2480×1300 panel averages to about 0.9987. Such
  defects are found on the element that owns the shadow, not on its ancestors.

**SSIM definition** for these numbers; M1 must use the same, or recalibrate:

- Non-overlapping 8×8 blocks on BT.601 luma (`0.299 R + 0.587 G + 0.114 B`), `C1 = (0.01·255)²`, `C2 = (0.03·255)²`,
  sample variance (n − 1), mean over blocks.
- Before comparing, pixels inside text boxes (inflated by 2 px, union of both captures) and `data-u-external` regions
  are copied from the golden into the Unity image (copy-mask).
- Per element: the mean over the blocks of the 8-px grid that overlap the region above.

`spike/m0-metrics.ts` is the reference implementation. The skip variant in `spike/compare-unity.ts` was used only for
the §2 column.

## 12. Other observations

- Auto-width text is wider in UI Toolkit: width = ceil of the advance width (190.50 → 191; 20.36 → 21; 61.08 → 62),
  and one real-bold case measured +1.95 px (196.05 → 198, cause unknown). Rows of auto-width texts accumulate it
  (f08: the third text starts 2.45 px later). Open item O-4.
- The sRGB-target run shows 0.04 % of pixels off by more than 3 in every fixture (0.00 % in the verifier setup); the
  region was not located. It does not affect the decisions.
- Shadows are absent in UI Toolkit, as expected; they are baked by the exporter in M1. Baked-shadow fidelity is not
  measured yet.
- Advanced text generator: same boxes and first-line baselines as standard for 1–3 lines, pitch floored to 1/64
  (R2); it logs an error if the internal `textInfo` is read (`TextHandle.textInfo should not be used with Advanced
  Text`), another reason to use the caret route.
